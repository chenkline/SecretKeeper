## 2. v0.0.1（当前实现范围）

## 3. v1.0.0 功能规划

### 3.1 二维码导出

**主密钥导出为二维码**

- 将已加密的主密钥字节流（格式同 `.smkexp`）编码为二维码。
- 生成一张图片：**上方**为主密钥 ID 与主密钥名称，**下方**为二维码。
- 编码方式：数字/字母模式以提高密度，**不做 Base64**（避免 33% 膨胀）。

**机密信息导出为二维码**

- 结构相同：上方为主密钥 ID 与机密信息标题，下方为二维码。

### 3.2 二维码导入

- 支持两种方式：**二维码图片导入**（选图片）与**扫描二维码**（调用相机）。
- 流程 = 原有导入流程 + 一个二维码解码步骤。解码后**与文件导入完全相同**。
- **只读取二维码区域，忽略图片上方的文字**（需求明确）。
- 分片处理：读取第一个二维码后，根据头部判断总片数，决定是否需要继续扫描后续二维码。

### 3.3 单条机密信息长度扩容

| 版本 | 上限 |
|---|---|
| 基础版 | 150 字符 |
| VIP | 1024 字符 |

**二维码分片**：1024 字符的密文（约 1.3KB）单个二维码放不下，需分片。

分片格式（数据层已定义）：

```
uint8   总片数
uint16  本片序号（从 0 开始）
uint8[] 分片载荷
```

第 0 片位于主二维码下方，后续片依次向下排列。导入时读第 0 片获得总片数，再按需扫描其余片。

**注意**：分片数量取决于二维码容量规格（版本、纠错等级）。建议用 **纠错等级 L（低）+ 高版本** 以最大化容量，并在 v1.0.0 实现时确定具体分片数上限。

### 3.4 SM2 国密

- 主密钥新增 SM2 选项，与 RSA-2048 并列。
- 格式已预留：`mkAlg = 2`。
- 各端需集成 GmSSL 或 BouncyCastle 等国密实现。
- **风险**：五端各自集成第三方国密库，一致性风险高。必须纳入黄金向量强制校验。

### 3.5 License 激活

**目标**：低成本激活 VIP（约 5 元/年）。

**限额分级**

| 状态 | 主密钥 | 机密信息 | 单条长度 |
|---|---|---|---|
| 未激活 | 2 | 15 | 150 |
| VIP（按费用等级） | 提高 | 提高 | 1024 | 无 |

**激活机制设计要求**

1. **低成本**：不能依赖昂贵的服务端。理想是**完全离线验证**。
2. **防篡改**：License 文件需签名，客户端内置公钥验签。
3. **不可伪造**：使用非对称签名，私钥**绝不**进入客户端。

**推荐方案：离线签名 License**

```
开发者侧（离线，有私钥）
  → 生成 License：含 [有效期, 功能等级, 设备指纹]
  → 用 Ed25519 私钥签名
  → 输出 License 文件 / 激活码

客户端（只有公钥）
  → 用户输入激活码 / 导入 License 文件
  → 用内置 Ed25519 公钥验签
  → 验签通过则按有效期与等级启用 VIP
```

**优点**：无需服务器、无需联网、激活码可离线分发、成本极低。

**待定事项**（v1.0.0 前需确认）：
- 费用等级的具体档位与对应限额
- 有效期策略（月付 / 年付 / 永久）
- 设备指纹的构成（避免因硬件变更导致失效）
- 是否允许同一 License 在多设备使用

**v0.0.1 的预留**：限额读取**必须**经由一个集中的 License/限额模块，v0.0.1 该模块固定返回基础版限额。这样 v1.0.0 只需替换实现，不需重构业务代码。

## 4. 预留接口清单

v0.0.1 实现时必须留出以下扩展点：

| 扩展点 | 位置 | 预留方式 |
|---|---|---|
| 限额来源 | 限额模块 | 集中函数，v0.0.1 固定返回基础值 |
| 主密钥算法分派 | 密码学层 | 按 `mkAlg` 枚举分派，未知值拒绝 |
| 导出载体 | 导出服务 | 返回字节流，二维码作为上层载体 |
| License 状态 | 限额模块 | 返回基础版 / VIP 两态 |

## 5. 跨版本数据兼容承诺

| 承诺 | 说明 |
|---|---|
| 向后兼容 | 新版本必须能读旧版本创建的**所有**数据文件 |
| 向前不兼容 | 旧版本读不了新文件是可接受的（会给出清晰提示） |
| 格式变更纪律 | 见[数据格式文档 §9](../03-data/数据格式与存储设计.md) |
| 五端同步 | 任一平台升版，其余四端必须同步支持同一格式版本 |

**绝不允许**：为了新功能而改变已有字段的含义。任何不兼容变更必须通过新增字段或提升版本号 + 迁移实现。

### 6.1 M1 交付内容

| 层 | 位置 | 自检项数 | 失败 | 跳过 |
|---|---|---|---|---|
| 密码学层 | `windows/src/crypto/` | 86 | 0 | 0 |
| 容器格式层 | `windows/src/container/` | （并入上层） | — | — |
| 存储层 | `windows/src/store/` | 81 | 0 | 0 |
| 核心层 | `windows/src/core/` | 178 | 0 | 0 |
| 业务层 | `windows/src/core/` | 54 | 0 | 0 |
| 黄金向量 | `scripts/verify-vectors.py` | 91 | 0 | — |

**RSA 覆盖盲区已消除。** 此前本机与 `windows-2022` runner 的 CNG 都不提供非对称算法，
RSA 生成、封装、解封装及依赖它们的业务流只能显式 SKIP（详见 [AGENTS.md](../../AGENTS.md) 第 9.4 节）。
密码学层换成 vendor 的 mbedTLS 3.6.7 后，RSA 为纯软件运算，**任何宿主上都能真实执行**，
业务层 54 项全部通过、**0 跳过**。

「跳过 0」现在是硬性门禁：任何一层出现 `skipped != 0` 都说明构建有问题，详见
[AGENTS.md](../../AGENTS.md) 第 9.6 节的自检基线表。

建议按此顺序：**先把一端做扎实并产出测试向量，再移植其余四端**。在测试向量就绪前大规模并行开发，会导致五个端各自发明不一致的格式，届时返工成本极高。
