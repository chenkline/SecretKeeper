# 总体技术设计

## 1. 设计目标

| 目标 | 具体要求 |
|---|---|
| 安全 | 磁盘上不存明文；密钥材料可清零；最小暴露时间 |
| 离线 | 运行时零网络访问，无遥测、无更新检查、无崩溃上报 |
| 跨平台一致 | 五端对同一份数据文件读写结果完全一致 |
| 可移植 | 密钥与数据文件在五端之间自由拷贝 |
| 可扩展 | 为 v1.0.0 的二维码、License 预留接口 |

## 2. 分层架构

五端对齐同一套分层。core 内部分四层，**依赖单向、无回边**：
crypto 与 serialize 互不依赖；store 只依赖 serialize；service 依赖三者；
UI 只依赖 service。

```
        UI（各平台原生界面）
             │  只调 service 门面
             ▼
        service（core 总入口）
        限额 / 退避 / KEK 缓存 / 文案映射
           │            │
           ▼            ▼
        store         crypto
        索引 + 文件    原语，无业务语义
           │
           ▼
        serialize
        字节 ↔ 内存对象
```

### 各层职责

**UI 层**：只负责呈现与输入。所有「能否执行」的判断（限额、是否默认主密钥、
要不要密码）由 service 给出结论后，UI 才据此禁用或提示。UI 不得发起密码学运算，
也不得持有密钥材料——它连 `crypto::Kek` 这个类型都不接触。
列表投影、黄色问号判定、退避文案等纯逻辑放在 UI 层的 `view_model` 中，
可在不启动 FLTK 事件循环的情况下测试。

**service 层**：唯一的业务决策点，也是 UI 可见的唯一 core 头文件。每个方法对应
需求文档中的一条功能（如「切换主密钥」）。负责：
- 校验限额与前置条件（限额常量只在此定义，v1.0.0 由 License 覆盖时只改这一处）；
- 持有内存中的 KEK 缓存与密码错误退避计数；
- 将底层错误码映射为需求文档规定的固定提示文案；
- 需要密码的操作只有一个入口，密码参数可空：空密码表示「用已解锁的默认 KEK」，
  若目标不是默认主密钥且未传密码则返回 `kNeedsPassword`，由 UI 弹框后重试同一调用。

**store 层**：SQLite 索引与数据文件的存取。经序列化层提供**对象级**读写
（`MasterKeyStore` / `SecretStore`），对 service 只暴露内存对象，
不暴露裸字节与格式细节。限额判定不在本层，存储层只如实计数。

**serialize 层**：字节与内存对象互转，不依赖 crypto。
`Id` / `Salt` / `Nonce` / `Tag` 由本层自持别名，连 crypto.h 都不 include。
字节级细节见数据格式文档。

**crypto 层**：纯粹的原语封装，无业务语义。随机数、ID 生成、Argon2id、
AES-256-GCM、RSA-OAEP、RSA 密钥生成。所有函数要求显式传入参数长度，
返回可清零的结果缓冲区。**不出现 `Kek` / `MasterKey` 等业务名词**，
「用程序随机密钥加解密 KEK」这类组合动作上浮到 service。详见密码学设计文档。

**分层门禁**：`scripts/check-layering.py` 静态断言上述方向不被回潮，已接入 CI。

## 3. 进程内状态与解锁模型

应用只有一个全局安全状态：**已锁定 / 已解锁**。

- **已锁定**：内存中不保留任何 KEK、数据密钥或明文。仅显示锁屏界面，输入默认主密钥密码解锁。
- **已解锁**：默认主密钥的 KEK 缓存在内存中（经程序随机密钥包裹，见下文），可以执行读取类操作。涉及非默认主密钥的操作，必须单独输入对应主密钥密码并临时派生 KEK，用完立即清零。
- **重新锁定**：闲置超时、用户手动锁定、应用进入后台（移动端）时触发。锁定后立即清空所有缓存密钥与界面上的明文。

### 默认主密钥 KEK 缓存

为避免用户每次查看机密信息都重新做 Argon2id，默认主密钥的 KEK 常驻内存，但按需求做以下加固：

1. 程序启动时生成随机对称密钥（**程序随机密钥**），用它 AES-256-GCM 加密默认主密钥 KEK，得到 KEK 密文。
2. KEK 密文与程序随机密钥分散存放在内存中的不同结构里，不存在一处同时包含两者的连续对象。
3. 内存中为 KEK 密文准备 **3 个备选槽位**。每次轮换时把 KEK 密文解密后用新程序随机密钥重新加密，并随机迁移到另一个槽位，原槽位不清除（作为诱饵）。
4. 轮换触发时机：每 30 秒定时器、每次解锁成功、每次从后台回到前台。
5. 锁定时，所有槽位与程序随机密钥立即清零。

该机制显著提高内存转储直接获得 KEK 的难度，但不替代锁屏密码保护。

### 密码错误退避

对任何需要输入主密钥密码的操作：
- 记录连续错误次数；
- 第 n 次失败后，下一次尝试前等待 `delay(n) = min(2^(n-1) 秒, 上限)`；
- **退避不永久锁死**，等待结束后用户永远可以继续尝试（需求明确要求）；
- 退避计时以内存状态实现，不落盘（落盘会给攻击者提供离线统计信息，且用户重启即可绕过，无意义）。

## 4. 限额

| 项目 | v0.0.1 上限 |
|---|---|
| 主密钥数量 | 2 |
| 机密信息条数 | 15 |
| 单条机密信息长度 | 150 字符 |

实现要求：
- 限额以**可配置常量**承载，集中在单一模块，不散落在业务代码里；
- 添加前校验，超限时提示用户先导出再删除；
- 校验在服务层执行，UI 不得自行判断条数。

## 5. 各平台技术选型

| 平台 | 语言 | UI | 密码学来源 |
|---|---|---|---|
| Windows | C++17 | FLTK 1.4.5 | **mbedTLS 3.6.7**（vendor）+ `vendor/argon2` |
| Linux | C++17 | FLTK 1.4.5 | **mbedTLS 3.6.7**（同一份 vendor 源码）+ `vendor/argon2` |
| macOS | C++17 | FLTK 1.4.5 | **mbedTLS 3.6.7**（同一份 vendor 源码）+ `vendor/argon2` |
| Android | Kotlin | Jetpack Compose | java.security（若选 mbedTLS 需 NDK 封装） |
| iOS | Swift | SwiftUI | CryptoKit / Security.framework |

Windows、Linux、macOS 三端固定使用 **mbedTLS 3.6.7**（源码 vendor 在 `vendor/mbedtls/`，Apache-2.0）。mbedTLS 是纯软件实现，**RSA 恒可用**，不需要探测宿主是否提供非对称算法。三端 UI 统一采用 **FLTK 1.4.5**（LGPL-2.1，源码 vendor 在 `vendor/fltk/`），静态链接，产物为不依赖任何第三方 DLL 的单文件可执行程序。Android / iOS **不强制**使用 mbedTLS，各自系统库即可，但必须逐字节通过同一份黄金向量。

桌面三端（Windows / Linux / macOS）**共享同一份业务与界面代码**（`src/common`、`src/include`、`src/app`），密码学与界面行为天然一致；Android 与 iOS 保持各自的原生实现，靠黄金向量强制对齐。

**关键约束**：即使各端密码学库不同，也必须产生**逐字节相同**的结果。因此：
- RSA-OAEP 的哈希算法固定为 SHA-256，不使用库默认哈希；
- AES-GCM 的 IV 固定 12 字节、Tag 固定 16 字节；
- Argon2id 参数固定，不使用库的"推荐值"；
- 所有随机数来自各端 CSPRNG，不使用 `Math.random()`、`rand()` 等非密码学随机源。

详细的一致性保障机制见测试与验收方案。

## 6. 扩展点预留

以下能力在 v0.0.1 **不实现**，但接口按下列方式预留，避免 v1.0.0 返工：

| 预留能力 | 预留方式 |
|---|---|
| SM2 国密 | 容器格式保留算法标识字段，密码学层以算法枚举分派 |
| 二维码导入导出 | 导出服务返回字节流，二维码编码作为其上层的另一种载体 |
| License 激活 | 限额读取经由 License 模块返回，v0.0.1 固定返回基础版限额 |

详见版本规划与扩展预留文档。

## 7. 关键设计权衡

| 决策 | 取舍理由 |
|---|---|
| 主密钥用 RSA 而非对称密钥直接当数据密钥 | 需求明确要求密钥对形态；RSA-2048 公钥仅 294 字节，导出文件可接受；OAEP 可封装 32 字节数据密钥 |
| Argon2id 而非 PBKDF2 | PBKDF2 在 GPU 上并行成本低，对离线爆破防护弱；Argon2id 同时抗 GPU 与旁路攻击，且满足 300ms/10MB 预算 |
| 每记录随机盐而非全局固定盐 | 兼顾"同密码同记录可跨端互认"与"不同记录 KEK 不同"，避免一处泄露全部泄露 |
| 自定义二进制容器而非 JSON | 二维码容量紧张，Base64 会使体积膨胀约 33%；二进制可直接切分进二维码 |
| SQLite 仅存索引，明文数据在独立文件 | 满足"数据库索引文件路径"要求；数据文件可单独导出、单独备份；SQLite 可安全加密或替换 |
| 五端不共享代码 | 需求明确要求；代价是实现量大、需强一致性测试约束 |
