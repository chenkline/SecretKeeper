# 数据格式与存储设计

> **本文档是跨平台数据一致性的唯一真相源。** 五端实现若与本文档冲突，以本文档为准，并修正实现。任何格式变更必须先修改本文档，再修改五端实现与测试向量。

## 1. 设计目标

| 目标 | 说明 |
|---|---|
| 跨端一致 | 五端对同一份文件产生完全相同的解析结果 |
| 自包含 | 密码学参数全部随记录保存，不依赖外部配置 |
| 可扩展 | 新增算法或字段不破坏旧版本解析 |
| 紧凑 | 为 v1.0.0 二维码导出预留容量效率 |
| 可认证 | 密文被篡改必须可检测 |

## 2. 通用编码规则

### 2.1 字节序与整数

- 所有多字节整数一律使用**大端序（Big-Endian, Network Byte Order）**。
- 不使用任何平台原生字节序。
- 无符号整型用 `uintN` 标注（N 为位数）。

### 2.2 长度前缀（TLV 约定）

变长字段统一编码为：

`uint32 长度` + `长度` 字节的载荷

长度为该字段载荷的字节数，**不包含**这 4 字节长度前缀本身。

### 2.3 字符串

- 编码：UTF-8，无 BOM。
- 允许包含 NUL 以外的任意字符。
- 由 TLV 承载，因此不需要结束符。
- 标题为空时，长度为 0。

### 2.4 机密信息明文的字符计数

需求中的"150 个字符"按 **Unicode 码点（code point）计数**，而非 UTF-16 单元或字节数。

- C++：按码点遍历（注意代理对）
- Swift：`String.count`
- Kotlin：`codePointCount`
- C：UTF-8 解码后统计

实现时必须在五端交叉验证同一字符串（尤其含 emoji、生僻字、组合字符时）计数一致。

## 3. 容器通用结构

主密钥文件与机密信息文件使用统一的容器外壳，便于统一版本管理。

```
┌────────────┬─────────────┬──────────────┬─────────────┐
│ Magic(4B)  │ Version(2B) │ Flags(2B)    │ PayloadLen  │
│ "SMK1"     │ 0x0001      │ 见 3.2       │ uint32      │
└────────────┴─────────────┴──────────────┴──────────────┘
┌───────────────────────────────────────────────────────┐
│ Payload (PayloadLen 字节)                             │
└───────────────────────────────────────────────────────┘
```

### 3.1 Magic

| 文件类型 | Magic（4 字节 ASCII） |
|---|---|
| 主密钥文件 | `SMK1` |
| 机密信息文件 | `SSC1` |

Magic 用于快速识别文件类型，**不提供安全性**（任何人都能改）。它的作用是让导入流程能给出清晰的"这不是密匣导出的文件"错误。

### 3.2 Flags

保留字段，v0.0.1 恒为 `0x0000`。为未来预留位。

### 3.3 Version

`uint16` 大端。当前为 `0x0001`。

解析规则：
- 版本**高于**程序支持的最高版本 → 拒绝导入，提示"导入失败，文件版本过高"。
- 版本**低于**程序支持的版本 → 若存在向下迁移路径则迁移，否则拒绝。
- 未识别的版本号一律拒绝，不做"尽力猜测"解析。

### 3.4 长度校验

解析前必须校验：
1. `PayloadLen` 与文件剩余实际长度一致，多余字节视为非法。
2. 每个 TLV 的长度前缀不超过剩余可用长度。
3. 所有固定长度字段长度精确匹配。

任一项不满足 → 解析失败，不得崩溃、不得越界读取。

#### 3.4.1 校验顺序与错误类别

上述三条不是并列的。**顺序不同，报出的错误类别就不同**，
而错误类别直接决定 UI 提示文案，因此顺序必须固定并写入规范。

**第 1 步：头部固定部分**（Magic → Version → Flags → PayloadLen 可读性）

| 情况 | 错误类别 |
|---|---|
| 文件短于 12 字节 | `truncated` |
| Magic 不匹配 | `bad_magic` |
| Version 高于 `0x0001` | `unsupported_version` |
| Flags 非 0 | `length_mismatch` |

**第 2 步：`PayloadLen` 合理性**

| 情况 | 错误类别 |
|---|---|
| `PayloadLen` 超过格式物理上界（4 KiB） | `length_mismatch` |

> 上界不是随意取值。主密钥 payload 实测约 1.6 KB，机密信息约 0.4 KB，
> 取 4 KiB 留约 2.4 倍余量。这一检查把「声明 9999 字节」判为长度字段非法，
> 与「声明 366 字节但文件只有 8 字节」区分开——两者都表现为实际短于声明，
> 但根因完全不同：前者是被篡改的长度字段，后者是文件内容缺失。

**第 3 步：算法标识**（仅主密钥文件的 `mkAlg`）

| 情况 | 错误类别 |
|---|---|
| `mkAlg != 1`（如 SM2 的 2） | `unknown_algorithm` |

> 这一步**必须早于长度一致性检查**。文件用了不支持的算法时，
> 那才是调用方最需要知道的原因；先报「长度不对」会让用户以为文件损坏，
> 而真实原因是版本不支持。
>
> 同样地，头部阶段**不能**要求 payload 至少有 4 字节才继续：
> 主密钥文件的第 1 个字节是 `mkAlg` 而非 TLV，只含 `mkAlg` 的极短文件
> 是合法的负例输入，若在头部就按长度拦下，就永远读不到那个要被拒绝的算法字节。

**第 4 步：长度一致性与字段解析**

| 情况 | 错误类别 |
|---|---|
| 实际长度 **大于** `PayloadLen`（尾部有多余字节） | `length_mismatch` |
| TLV 长度前缀读不到（文件在此之前就断了） | `truncated` |
| TLV 长度前缀声明的长度超过合理上界 | `length_mismatch` |
| TLV 长度前缀可信，但剩余字节不足 | `truncated` |
| 固定长度字段长度不等于期望值 | `length_mismatch` |
| 解析成功后仍有未消费的字节 | `length_mismatch` |

> 实际短于 `PayloadLen` 时不在此步直接失败，而是交给字段级判定：
> 只有字段层知道某个 TLV 该出现在哪个位置、占多少字节，
> 因此只有它能区分「长度字段被篡改」与「文件内容缺失」。

**第 5 步：语义校验**

| 情况 | 错误类别 |
|---|---|
| `pubKeyNonce == privKeyNonce` | `length_mismatch`（安全缺陷，必须拒绝） |
| `name` / `title` 不是合法 UTF-8 | `invalid_utf8` |

> 公私钥 nonce 相同属于安全缺陷而非格式错误，但当前版本没有独立的
> 错误类别可归，暂归入 `length_mismatch`。若将来需要给用户更准确的提示，
> 应新增 `nonce_reuse` 类别而不是复用长度错误。

## 4. 主密钥文件格式（Magic = "SMK1"）

```
Payload:
  uint8   mkAlg          主密钥算法标识
  TLV     masterKeyId    主密钥 ID（16 字节二进制，非文本）
  TLV     name           主密钥名称（UTF-8，可为空；仅用于显示，不参与加解密）
  TLV     salt           Argon2id 盐（16 字节）
  uint32  kdfMem         Argon2id 内存参数（KiB），10240
  uint32  kdfIter        Argon2id 迭代次数，3
  uint32  kdfPar         Argon2id 并行度，1
  uint8   pubKeyEncAlg   公钥加密算法标识，固定 1 = AES-256-GCM
  TLV     pubKeyNonce    公钥 AES-GCM Nonce（12 字节，独立随机，不可与 privKeyNonce 相同）
  TLV     pubKeyTag      公钥 AES-GCM 认证标签（16 字节）
  TLV     pubKeyCipher   公钥密文（PKCS#1 DER 的加密结果）
  uint8   privKeyEncAlg  私钥加密算法标识，固定 1 = AES-256-GCM
  TLV     privKeyNonce   私钥 AES-GCM Nonce（12 字节）
  TLV     privKeyTag     私钥 AES-GCM 认证标签（16 字节）
  TLV     privKeyCipher  私钥密文（PKCS#8 DER 的加密结果）
```

### 4.1 字段说明

| 字段 | 说明 |
|---|---|
| `mkAlg` | 1 = RSA-2048；2 = SM2（**v1.0.0 预留，v0.0.1 必须拒绝**） |
| `masterKeyId` | 16 字节随机数生成，UI 中显示为十六进制或 Base32 字符串 |
| `name` | 用户自定义名称，**允许为空**。仅用于界面显示，**不参与任何加解密运算，不纳入 AAD** |
| `salt` | 明文存储，这是跨端一致的前提 |
| `pubKeyCipher` | PKCS#1 DER 公钥经 AES-256-GCM(KEK) 加密结果。**公钥与私钥一并加密存储**，避免密钥材料在磁盘上明文暴露 |
| `privKeyCipher` | PKCS#8 DER 私钥经 AES-256-GCM(KEK) 加密结果 |
| GCM AAD | 公钥与私钥均为 `masterKeyId` 的原始 16 字节 |

### 4.2 KDF 版本字段说明

Argon2id 版本号 `0x13` 为固定常量，**不单独占字段**——它隐含于 `kdfAlg = 1`。若未来需要支持其他 KDF，通过新增算法标识实现。

### 4.3 公私钥解密流程

```
1. 读 salt、kdfMem、kdfIter、kdfPar
2. KEK = Argon2id(password, salt, m, t, p, outlen=32)
3. pubKeyDer = AES-256-GCM-Decrypt(KEK, pubKeyNonce, AAD=masterKeyId,
                                    pubKeyCipher, pubKeyTag)
   → 失败则密码错误
4. privKeyDer = AES-256-GCM-Decrypt(KEK, privKeyNonce, AAD=masterKeyId,
                                     privKeyCipher, privKeyTag)
   → 失败则密码错误
5. 解析 PKCS#1 DER 得到公钥，解析 PKCS#8 DER 得到私钥
6. 清零 KEK、pubKeyDer、privKeyDer
```

> **公钥与私钥使用同一 KEK，但 nonce 必须各自独立随机生成。**
> 若复用同一 nonce，GCM 的密钥流完全相同，攻击者无需任何密钥即可由
> `pubKeyCipher XOR privKeyCipher` 直接恢复公钥与私钥的异或值，机密性彻底失效。

> ⚠️ **解密输出缓冲区长度 = 密文长度，不含 Tag。** GCM 是流模式，密文长度与明文长度**相等**，
> `pubKeyTag` / `privKeyTag` / `dataTag` 是独立字段，不参与密文长度计算。若按「密文字段总长」
> 分配输出缓冲区，恢复出的明文尾部会多出 16 个零字节，导致 DER 解析器直接拒绝。实现须用统一的 `plain_size(cipher)` 计算（见 `windows/src/core/master_key_service.cpp`）。

## 5. 机密信息文件格式（Magic = "SSC1"）

```
Payload:
  TLV     secretId       机密信息 ID（16 字节）
  TLV     masterKeyId    所属主密钥 ID（16 字节）
  TLV     title          标题（UTF-8，可为空；仅用于显示）
  TLV     wrappedDk      被主密钥公钥封装的数据密钥
  TLV     dataNonce      AES-GCM Nonce（12 字节）
  TLV     dataTag        AES-GCM 认证标签（16 字节）
  TLV     dataCipher     机密信息密文
```

### 5.1 字段说明

| 字段 | 说明 |
|---|---|
| `masterKeyId` | 关联主密钥。**明文存储**，这样列表页无需解密即可显示主密钥 ID |
| `title` | 可选标题，为空时长度为 0 |
| `wrappedDk` | `RSA-OAEP-SHA256(主密钥公钥, 数据密钥)`，长度 = 模长/8 = 256 字节 |
| `dataCipher` | `AES-256-GCM(数据密钥, dataNonce, AAD=secretId, 机密信息UTF-8)` |
| GCM AAD | `secretId` 的原始 16 字节 |

### 5.2 为什么主密钥 ID 与标题明文存储

列表页需要显示主密钥 ID 并与本地主密钥比对。若加密存储，每次列表查询都要解密全部记录，性能不可接受。ID 与标题本身不是机密。

但需在隐私提示中告知用户：**标题不加密**。这是明确的取舍。

#### 未找到主密钥的标识语义

**唯一标识是主密钥 ID 列值末尾的黄色问号，与名称列是否为空无关。**

- 问号属于**主密钥 ID 列**的列值，紧跟 ID 之后；该列宽度固定
- **主密钥名称列与问号无因果关系**：未找到主密钥时名称为空；找到但主密钥名称本身为空时名称同样为空
- 两种"名称为空"的情形必须依靠问号区分，不可混淆
- 标题列同理：无标题即留空，不参与任何标识逻辑

| 情形 | 主密钥 ID 列 | 主密钥名称列 |
|---|---|---|
| 主密钥存在且名称非空 | ID | 名称 |
| 主密钥存在但名称为空 | ID（**无问号**） | 空 |
| 主密钥不存在（悬空引用） | ID + **黄色问号** | 空 |

### 5.3 解密流程

```
1. 读 masterKeyId，在本地主密钥库中查找
   → 找不到则"导入失败，请先导入主密钥"
2. 取出该主密钥，用密码派生 KEK，解出 RSA 私钥
3. dataKey = RSA-OAEP-SHA256-Decrypt(主密钥私钥, wrappedDk)
4. plaintext = AES-256-GCM-Decrypt(dataKey, dataNonce, AAD=secretId,
                                   dataCipher, dataTag)
5. 清零 dataKey
```

任一步失败 → "导入失败，解密错误"。

## 6. 索引库（SQLite）

按需求，主密钥与机密信息的索引保存在**单个 SQLite 数据库**中，每条记录索引其数据文件路径。

### 6.1 数据库位置

| 平台 | 路径 |
|---|---|
| Windows | `%APPDATA%\Secret\secret.db` |
| Linux | `~/.local/share/SecretKeeper/secretkeeper.db` |
| macOS | `~/Library/Application Support/SecretKeeper/secretkeeper.db` |
| Android | app 私有目录 `/data/data/<pkg>/databases/secret.db` |
| iOS | app 容器 `Library/Application Support/SecretKeeper/secretkeeper.db` |

数据文件放在同目录下的 `keys/` 与 `secrets/` 子目录。

### 6.2 数据文件命名

- 主密钥：`keys/<masterKeyId 十六进制>.smk`
- 机密信息：`secrets/<secretId 十六进制>.ssc`

文件名由 ID 派生，无随机性，便于人工排查与备份。

### 6.3 表结构

```sql
-- 应用级元信息
CREATE TABLE app_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- app_meta['default_master_key_id'] 存默认主密钥 ID
-- app_meta['db_format_version']    存库格式版本
-- app_meta['lock_policy']          存闲置锁定时长等

CREATE TABLE master_keys (
    master_key_id TEXT PRIMARY KEY,   -- 32 位十六进制字符串
    name          TEXT NOT NULL,
    file_path     TEXT NOT NULL,      -- 相对数据目录的相对路径
    mk_alg        INTEGER NOT NULL,   -- 1=RSA-2048
    is_default    INTEGER NOT NULL,   -- 0/1
    created_at    INTEGER NOT NULL,   -- Unix 毫秒
    updated_at    INTEGER NOT NULL
);

CREATE TABLE secrets (
    secret_id     TEXT PRIMARY KEY,   -- 32 位十六进制字符串
    master_key_id TEXT NOT NULL,       -- 允许悬空：主密钥可能已被删除
    title         TEXT NOT NULL DEFAULT '',
    file_path     TEXT NOT NULL,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL
);

CREATE INDEX idx_secrets_mk ON secrets(master_key_id);
```

### 6.4 关键约束

- **允许悬空引用**：删除主密钥时**不删除**其加密的机密信息（需求明确要求）。因此 `secrets.master_key_id` **不建外键约束**。UI 遇到悬空引用时显示黄色问号。
- `is_default` 的唯一性由服务层事务保证。
- **不存储任何密钥材料、密码、盐或明文机密信息**，公钥也不例外（公钥随主密钥文件密文保存，索引库不新增公钥列）。索引库泄露不应导致机密泄露（仅泄露 ID、名称、标题与存在性）。

### 6.5 数据库文件本身

索引库**不加密**（v0.0.1 范围外）。其中仅有 ID、名称、标题等元数据。但需在威胁模型中如实说明：**索引库泄露会暴露"用户有哪些条目、标题是什么"**。

若后续需要，可用 SQLCipher 加密，或将标题改为加密存储。

## 7. 导入导出格式

### 7.1 导出

导出内容 = 对应数据文件的**完整原始字节流**，逐字节一致（需求 3.3 要求"导出内容与机密信息文件内容完全一致"）。

**扩展名约定**（内容本身与本地文件完全相同，仅扩展名区分）：
- 主密钥：`.smkexp`
- 机密信息：`.sscexp`

使用独立扩展名而非 `.smk`/`.ssc`，可防止用户把导出文件误放回数据目录被当作真实记录直接加载。

### 7.2 导入

导入时**保留原有的 ID**；若与本地已有记录 ID 冲突，则重新生成新 ID。理由：
- 保留 ID 可使"导出→导入"往返后数据完全一致，便于测试与用户核对；
- 冲突时重新生成可避免覆盖本地记录。

导入同时必须：写入新的数据文件、更新索引库、校验限额。

### 7.3 导出文件的密码学差异

导出时使用**独立的保护密码**派生 KEK，并使用**新生成的盐**，因此：

- 导出文件的 `salt` 与本地记录不同；
- 导出文件的 `pubKeyCipher` 与 `privKeyCipher` 均是用保护密码的 KEK 加密的，且各自使用独立随机 nonce；
- `masterKeyId`、`name` 与本地记录相同（公钥密文因保护密码不同而不同，但其明文内容与本地一致）。

导入时用保护密码解开公钥与私钥，再用新的主密钥密码、新盐与两个新 nonce 重新加密保存。

## 8. 二维码格式预留（v1.0.0）

本节仅描述数据层预留，交互见版本规划文档。

- 导出的字节流**直接**作为二维码载荷（**不再 Base64**，因为 Base64 会膨胀约 33%，浪费容量）。
- 二维码采用数字/字母模式编码以提高密度。
- 分片：载荷前加 5 字节头 `uint8 总片数` + `uint16 本片序号`。
- 导入时读第一片，根据总片数判断是否需要继续扫描。
- 导入时**只读二维码区域**，忽略图片上方的文字（需求明确）。

## 9. 版本演进规则

> **当前版本：Magic = `SMK1` / `SSC1`，`Version` = `0x0001`。**
> 密码学实现的替换（如 CNG → mbedTLS）**不涉及数据格式变更**，因此不升版本号。
> 任何升版都必须由用户明确指示。

| 变更类型 | 处理方式 |
|---|---|
| 新增可选字段 | 提升 Version，旧版本解析时按默认值处理 |
| 新增算法（SM2） | 新增算法标识值，旧版本遇到未知值时**拒绝**并给出清晰提示 |
| 修改字段语义 | **禁止**。必须新增字段或提升版本并提供迁移 |
| 改变字节布局 | **须经用户明确指示**后才提升 Magic 或 Version；在此之前一律原地修改格式 |

**禁止向后不兼容地修改已有字段的含义。** 这是保证旧数据永远可读的唯一途径。

### 9.1 版本号与 Magic 的使用约定

**在用户明确指示升版本之前，Magic 恒为 `SMK1`/`SSC1`，Version 恒为 `0x0001`，格式变更一律原地进行。**

理由：v0.0.1 尚未产生任何实现与存量数据，升版本只会带来无谓的兼容负担。本轮修订（公钥改为密文存储、删除机密信息侧冗余算法字段）即属于原地修改，未升版本。

仅当满足以下任一条件、**且用户明确指示**时，才提升 Magic 或 Version：
- 已发布版本的数据需要被保留并继续可读
- 字段语义发生不可兼容的变化
- 需要引入与现有布局冲突的新结构
